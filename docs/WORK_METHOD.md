# منهجية العمل: فحص ← تنفيذ ← تحقق ← تسليم

عقد إلزامي لكل مزود (API أو ويب) يعمل داخل Lion AI. غايته أن يُكمل أي مزود عمل سابقه من النقطة نفسها، وأن لا يضيع شيء عند نفاد الحصة.
النسخة المختصرة التي تُحقن في تعليمات المزود موجودة في `WorkMethod.kt`، وهذا الملف هو المرجع الكامل.

## 0) مبادئ
1. **الدليل قبل الادعاء**: لا يُقال «تم» إلا بعد نتيجة أداة تثبت ذلك (قراءة الملف بعد الكتابة، حالة التشغيل بعد الدفع).
2. **افحص قبل الإنشاء**: لا تفترض أن مجلداً أو فرعاً أو ملفاً غير موجود (أو موجود).
3. **خطوة صغيرة ← تحقق ← سجّل**: لا تجمع عدة تعديلات غير متحقَّق منها.
4. **كل عملية قابلة للإعادة (idempotent)**: إعادة تنفيذ الخطوة بعد انقطاع لا تُفسد شيئاً ولا تكرر عملاً.
5. **الخطأ الأول هو السبب غالباً**: عالج أول خطأ، لا آخر خطأ.

## 1) بداية أي عمل (استئناف أو جديد)
1. اقرأ سياق الجلسة وحزمة الترحيل إن وُجدت (`checkpoint_list` / `checkpoint_resume` / `memory_search`).
2. **تحقق من الواقع لا من الوصف**: ما كتبه المزود السابق «نجح» يُتحقق منه بقراءة الحالة الفعلية (الملف، الفرع، آخر تشغيل) قبل البناء عليه.
3. اكتب سطراً واحداً: «الهدف / المنجز المتحقَّق منه / الخطوة التالية».

## 2) إنشاء المجلدات والملفات
| الخطوة | الأداة | الفحص |
|---|---|---|
| قبل | `file_stat` / `github_list_dir` | هل المسار موجود؟ نوعه (ملف أم مجلد)؟ |
| تنفيذ | `file_mkdir` ثم الكتابة | أقل تعديل كافٍ؛ للتعديل الجزئي patch لا إعادة كتابة كاملة |
| بعد | `file_stat` ثم `file_verify` | الحجم > 0، الأسطر المتوقعة، لا ملف فارغ ولا مكرر |
- ملف موجود: اقرأه أولاً ثم عدّله؛ لا تستبدله دون قراءة.
- لا تحذف ولا تنقل ملفاً قبل التأكد أن لا شيء يشير إليه (`github_search_code` / بحث نصي).

## 3) الفروع و GitHub
**قبل أي كتابة:** `github_whoami` (التوكن صالح؟) ← `github_repo_overview` ← `github_list_branches`.

1. **فرع جديد**: إن كان الاسم موجوداً فتابع عليه (لا تنشئه ثانية)؛ وإلا `github_create_branch` من آخر commit في الفرع الأساسي، ثم تحقق بـ `github_list_branches`.
2. **ملف**: `github_read_file` للحصول على الإصدار الحالي؛ تعديل ملف موجود يستخدم أحدث إصدار له، وإنشاء ملف جديد لا يحتاجه. عند تعارض (409/422) أعد القراءة وأعد التطبيق على الأحدث، لا تتجاهل الخطأ.
3. **عدة ملفات**: `github_commit_files` أو `github_push_workspace` بـ `dry_run=true` أولاً، راجع الفرق، ثم نفّذ. commit واحد لكل وحدة منطقية.
4. **لا تدفع إلى `main` مباشرة** إلا بطلب صريح من المستخدم؛ استخدم فرعاً + PR.
5. **لا force-push ولا حذف فرع** دون طلب صريح.
6. **بعد الدفع**: `github_wait_run` ← إن فشل: `github_job_log` وخذ **أول** خطأ ← أصلح ← ادفع ← أعد الانتظار. 3 محاولات إصلاح كحد أقصى لنفس الخطأ، ثم أبلغ المستخدم بنص الخطأ الحرفي واقتراح محدد.
7. أخطاء الصلاحيات: `401` توكن غير صالح، `403` صلاحية ناقصة أو حد معدل (اقرأ الرسالة)، `404` مسار/مستودع/فرع غير موجود أو لا صلاحية عليه. لا تكرر الطلب نفسه أكثر من مرة دون تغيير شيء.
8. **حد المعدل**: توقف عن إصدار طلبات جديدة، احفظ الحالة، وأبلغ.

## 4) الاختبار واستكشاف الأخطاء
1. أعد إنتاج الخطأ (أو اقرأ السجل الحرفي) قبل التعديل.
2. حدّد السبب الجذري: افتح الملف والسطر، وابحث عن كل موضع متأثر.
3. أصغر إصلاح للسبب لا للعَرَض. لا تحذف اختباراً ولا تُضعف تأكيداً لإنجاحه.
4. أعد التحقق: `gate_run` / اختبار / بناء، وتأكد أن الخطأ اختفى ولم يظهر غيره.
5. إن لم يتقدم الإصلاح بعد محاولتين مختلفتين: توقف، لخّص ما جُرّب، واطلب توجيهاً.

## 5) نفاد الحصة والانتقال بين المزودات
التطبيق يصنّف الأخطاء ويبدّل المزود تلقائياً من السجل نفسه (`QuotaGuard`):
| النوع | التصرف | التبريد |
|---|---|---|
| حد مؤقت (429) أو خطأ عابر | إعادة محاولة مرتين بانتظار متزايد على المزود نفسه | 90 ث |
| نفاد حصة/رصيد | تبديل فوري لمزود بديل | 6 ساعات |
| مفتاح غير صالح | تبديل + تنبيه المستخدم | 30 د |

قواعد على المزود:
1. **احفظ الحالة بعد كل وحدة منجزة** (`checkpoint_save` / ملاحظة جلسة) فلا يضيع شيء إن انقطعت الحصة بعد الخطوة مباشرة.
2. إن ظهرت علامات اقتراب النفاد فلا تبدأ وحدة كبيرة جديدة؛ أنهِ الحالية وسلّم حالة واضحة.
3. **المزود الخلَف**: لا تعد خطوة نجحت، لا تبدأ من الصفر، تحقق من آخر خطوة بالقراءة (البند 1) ثم تابع.
4. إن نفدت كل المزودات: يحفظ التطبيق الحالة، ويكفي أي رد من المستخدم لاحقاً (أو من مزود جديد) للمتابعة من النقطة نفسها.

## 6) رسائل المستخدم أثناء التنفيذ
1. السؤال أثناء العمل: أجب بإيجاز (≤3 أسطر) ثم تابع من النقطة نفسها دون إعادة الخطوات.
2. الملاحظة أو التعديل المطلوب: نفّذه عند أقرب نقطة آمنة بين خطوتين، ولا تقطع عملية كتابة جارية.
3. التعارض مع المهمة الحالية: اذكر ذلك صراحة واسأل مرة واحدة فقط.
4. في تقرير نهاية المرحلة: اذكر كل ملاحظة وصلت وماذا حدث لها (نُفّذت / أُجّلت ولماذا).

## 7) التقرير الختامي (ثابت)
1. **ما أُنجز وتحقق**: كل بند مع دليله (ملف، أو نص الخطأ الحرفي، أو رابط التشغيل).
2. **ما تعذّر**: السبب الجذري والخطوة التالية المقترحة.
3. **ما لم يُتحقق منه**: بصراحة (لم يُبنَ، لم يُجرَّب على جهاز…).
4. **الحالة للاستئناف**: أين توقفنا، وماذا يفعل المزود التالي أولاً.
لا ادعاء نجاح دون نتيجة أداة فعلية، ولا طباعة المفاتيح أو التوكنات في أي مكان.

## 8) قائمة تحقق قبل التسليم
- [ ] كل ملف جديد/معدّل تُحقق منه بقراءته بعد الكتابة.
- [ ] `gate_run` أخضر، و`secret_scan` نظيف قبل أي دفع.
- [ ] CI أخضر، أو سبب الفشل مذكور بنصه مع خطة.
- [ ] التقرير الختامي مكتمل بأقسامه الأربعة.
