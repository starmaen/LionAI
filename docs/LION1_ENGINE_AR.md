# Lion-1 — المحرّك المدمج (مزوّد يعتمد على نفسه)

آخر تحديث: 2026-11-14 · الملفات: `LionEngine.kt` · `LionEngineUi.kt` · `LionOne.kt` · `docs/LION1_ENGINE_AR.md`

## المشكلة التي حلّها هذا التغيير

قبل هذا التحديث كان `lion-1` **واجهة تمرير**: يجمع رسالة المستخدم ويضيف الهوية، ثم يرسلها إلى
مزوّد خلفي — إما `127.0.0.1:44045` (خادم لم يكن التطبيق يشغّله) أو بوابة Cloudflare/worker.
أي أن lion-1 لم يكن يملك عقلاً ولا قدرة، وكان يتوقف تماماً إذا غاب المزوّد الخلفي.

الآن lion-1 = **محرّك استدلال حقيقي داخل التطبيق**:

```
رسالة المستخدم
   │
   ├─ Lion-1 (هوية + توجيه مهمة: code/teach/write/reason/translate/summary)
   │
   ├─ 1) المحرّك المدمج على الجهاز  ── llama-server (llama.cpp) داخل Alpine/proot
   │        • النموذج: GGUF في مساحة العمل (models/lion/*.gguf)
   │        • المنفذ: 127.0.0.1:44045 — /v1/chat/completions + tools (function calling)
   │        • بلا إنترنت بعد التنزيل، بلا مفتاح، بلا بوابة
   │
   ├─ 2) خادمك (Base URL في إعدادات lion-1)  ── إن وضعت رابطاً
   ├─ 3) خادم محلي 127.0.0.1:44045            ── إن شغّلت llama.cpp بنفسك
   └─ 4) البوابة الخارجية                     ── آخر مسار احتياطي (يبقى معطّلاً افتراضياً)
```

## لماذا llama.cpp داخل Alpine وليس مكتبة native؟

- التطبيق يملك أصلاً بيئة Alpine حقيقية عبر proot (`LinuxEnv`) ويشغّل فيها خوادم (OpenCode).
  إضافة `llama-server` إليها لا تحتاج NDK ولا مكتبات جديدة ولا إعادة بناء كود C++ داخل APK.
- الحزمة موجودة رسمياً في مستودع Alpine: **`llama-server`** (community، إصدار 3.24 الحالي)،
  فيصبح التثبيت أمراً واحداً: `apk add --no-cache llama-server`.
- llama-server يقدّم واجهة متوافقة مع OpenAI، وبوجود `--jinja` يدعم **tools** الأصلية،
  فيستفيد lion-1 من أدوات التطبيق بنفس مسار `custom` بدل بروتوكول نصي فقط.

## خطوات التشغيل (مرة واحدة)

1. **البيئة المحلية** ← «⬇️ تحميل وتفعيل» (Alpine + أساسيات).
2. بطاقة **🦁 محرّك Lion-1 المدمج** ← «📦 تثبيت المحرّك» (ينزّل حزمة llama-server داخل Alpine).
3. «⬇️ تنزيل النموذج» (افتراضياً Qwen2.5-1.5B-Instruct Q4_K_M ≈ 940MB، قابل للاستئناف).
4. «▶️ تشغيل» ثم «🧪 اختبار» — المتوقع: «✅ المحرّك يعمل» مع رد قصير من النموذج.
5. في الشات اختر المزود **🦁 Lion-1** (والوضع المناسب: عام/كود).

بعد الخطوة 4 لا حاجة لأي مزوّد أو إنترنت: الاستدلال يجري على الجهاز.

## النماذج

| المعرّف | الأساس | الحجم | ملاحظة |
|---|---|---|---|
| `lion-1-mini` (افتراضي) | Qwen2.5 1.5B Instruct · Q4_K_M | ≈940MB | هواتف 4–6GB · الأسرع |
| `lion-1-base` | Qwen2.5 3B Instruct · Q4_K_M | ≈1.9GB | أذكى في البرمجة · 8GB+ |
| مخصص | **نموذجك أنت** | حسب الملف | ضع رابط GGUF أو مسار ملف |

### استخدام نموذج Lion-1 المدرَّب فعلياً

بعد تدريب LoRA وتصديره GGUF (`model/train_lora.py` → `merge_export.py` → تحويل GGUF):

1. ارفع الملف إلى HuggingFace (أو ضعه على الجهاز).
2. في بطاقة المحرّك: «＋ نموذج مخصص» ← ضع رابط `resolve/main/...gguf` أو المسار المحلي ← «حفظ».
3. «⬇️ تنزيل النموذج» (يُتخطّى إن كان الملف موجوداً) ثم «▶️ تشغيل».

الهوية Lion-1 تُحقن من التطبيق في كل الحالات، فإن درّبت النموذج على هوية «أسد» ستتضافر مع
تعليمات التطبيق بدل أن تتعارض معها.

## أدوات التطبيق من داخل lion-1

- **function calling أصلي**: `LlmClient.askWithTools` يوجّه `provider == "lion1"` إلى
  `callLionOneTools` الذي يستدعي llama-server بـ `tools` ويعيد `tool_calls` إلى `ToolAgent`.
- **مجموعات الأدوات كاملة**: lion-1 يُعامل كمزود محلي (مثل `custom`) فيأخذ كل المجموعات
  (ملفات، شل، ويب، GitHub، قواعد بيانات…) مع سقف تعليمات أصغر (12K حرف) لأن سياق النموذج المحلي محدود.
- **أداة إدارة المحرّك**: `lion_engine` (المجموعة SHELL) — يستطيع الوكيل بنفسه:
  `status` / `models` / `install` / `download` / `start` / `stop` / `test`.
- **fallback تلقائي**: إذا رفض المسار الحالي `tools` يعود lion-1 للرد النصي، فيكمل
  `ToolAgent` ببروتوكول `[[TOOL]]{...}[[/TOOL]]` كما هو مصمَّم — لا تتعطّل الجلسة.

## الاستدلال على الحالة والأخطاء

- `LionEngine.phase`: `LINUX_MISSING` → `SERVER_MISSING` → `MODEL_MISSING` → `READY` →
  `STARTING` → `RUNNING` / `ERROR`. رسالة الفشل تذكر **ما ينقص فعلاً**، لا «فشل الشبكة».
- رسالة `LionHint.nextStep()` تُعرض للمستخدم عند تعذّر كل المسارات، ومعها البديل الفوري.
- كل تشغيل يترك آخر 40 سطراً من مخرجات llama-server ظاهرة في البطاقة (سبب التوقف غالباً هنا:
  ذاكرة غير كافية للنموذج أو للسياق).

## استكشاف الأخطاء

| العرض | السبب المرجّح | الحل |
|---|---|---|
| «بيئة Linux غير مفعّلة» | Alpine لم تُنزَّل بعد | البيئة المحلية ← تحميل وتفعيل |
| فشل `apk add llama-server` | حزمة غير متوفرة في إصدار التوزيعة | يُعاد المحاولة تلقائياً بإضافة مستودع `v<الإصدار>/community` صراحةً؛ راجع «🔎 تشخيص» |
| «توقف llama-server قبل الجاهزية» | ذاكرة غير كافية / ملف GGUF تالف | جرّب `lion-1-mini`، أو أعد تنزيل النموذج، أو أنقص السياق إلى 4096 |
| يعمل لكن الرد بطيء | خيوط قليلة أو جهاز ضعيف | ارفع الخيوط (نصف الأنوية) وأنقص السياق |
| «المنفذ 44045 مشغول» | خادم آخر يستخدم المنفذ | «⏹️ إيقاف» ثم أعد التشغيل، أو أوقف الخادم الآخر |
| أدوات لا تُستدعى | السياق صغير فقُصّت التعليمات | ارفع السياق إلى 8192/16384 أو ابدأ محادثة جديدة |

## ملاحظات تقنية

- `LionEngine.routes` و`LionOne.buildRoutes` دالتان صرفتان (بلا سياق أندرويد) لتكونا قابلتين
  للاختبار: `app/src/test/java/com/lion/ai/LionEngineRoutesTest.kt`.
- المحرّك والخادم المحلي يتشاركان المنفذ 44045، لذا يُدمج المساران تلقائياً عند وجود المحرّك.
- `stop()` يقتل عملية proot ثم `pkill -f llama-server` احتياطاً (بعد إعادة تشغيل التطبيق لا نملك
  مقبض العملية القديمة).
- التنزيل يستخدم `Range` للاستئناف ويكتب في `*.part` ثم يعيد التسمية، فلا يُشغَّل ملف ناقص أبداً.
